# コードのレビューで、名前を確かめる（すべてのプロジェクトのためのルール。言語に共通）

- コードを点検するときは、名前も確かめる（ユーザーに頼まれたレビュー、`/code-review`、Claude が自分で書いたコードの見直しの、どれでも）。
  - 理由: 2026-11-02 に、ユーザーが「コードレビューのチェックポイントとしても意識してほしい」と指示した。
- 確かめる観点は、言語ごとのルールに書いてある（Python は `~/.claude/rules/python-descriptive-names.md`、C++ は `~/.claude/rules/cpp-descriptive-names.md`）。
- 次の名前を見つけたら、ファイル、行、名前の案を添えて指摘する。
  - 一語だけの名前。略語だけの1語の名前（`cnt`、`res`）も含む（変数名は2語以上で作る。3〜4語以上は目指す目安であり、2語の名前は、それだけでは指摘しない）。
  - ソフトウェアエンジニアに通じる略語（`mic`、`vlm`、`cnt`、`res` など）を使っていること自体は、指摘しない。
  - 何の値か分からない名前。
  - 文脈の上で大事な意味（その値がどこから来たか、など）ではなく、処理の手順だけを表している名前（例: 別のサーバーから取得した文に `dequeued_prompts` → `fetched_prompts`）。
  - 目的語のない、動詞だけの関数名（例: `_care_once` → `_care_for_worker_once`）。
  - 情報を足しすぎて、文の形になっている変数名や関数名（真偽値の名前を除く。例: `vlm_selected_function` → `selected_function_by_vlm`）。
  - 動詞を含むのに、動作主か目的語の情報がない変数名（例: `selected` → `selected_function_by_vlm`）。
  - 名詞だけの変数名で、ほかの動作の主語になるか目的語になるかが分からず、能動か受動かの情報を足すと理解を助けるもの（例: `prompts` → `taken_prompts`）。
  - 何が真なのかが読み取れない真偽値の名前（例: `seated` → `worker_is_seated`）。
  - 語と語の間を `_` でつないでいない、変数名と関数名（クラス名などの型の名前は対象外。C++ で既存のプロジェクトが別の書き方で揃っているときは、`~/.claude/rules/cpp-descriptive-names.md` に従う）。
  - Python で、1つのファイルの中でしか使わないのに、先頭に `_` がない関数と定数。
  - 型や、文脈で分かることを繰り返している、冗長な名前（例: `taken_prompts_list`）。
- 名前を長くすることだけが目的の指摘はしない。
  - 理由: 2026-11-03 に、ユーザーが「無駄に冗長である必要はない」と指示した。
- レビューでは、名前の指摘を、細かな指摘として後回しにしない。
  - 理由: 2026-11-02 に、ユーザーが「命名は非常に大事です」と指示した。
- 名前を指摘したあとで、直すかどうかは、プロジェクトのルールにも従う。
