# robo_system の仕様書、設計書、実装の記録（ROBO_NEXT のためのルール）

- 書く先は、各文書の冒頭の「この文書について」を読んで決める。
- 仕様書には、外から見た振る舞いを書く。
- 設計書には、内部の構造を書く。
- ADR には、決定の理由を書く。
- 実装の記録には、まだ決まっていないことと、試験の記録を書く。
- 仕様書（01、02）に、プロセス、スレッド、通信方式を書かない。
- 設計書には、いま有効な設計だけを書く（古い設計を、取り消し線や「以前は〜」の形で残さない）。
- 設計書のアーキテクチャの決定には、ADR の ID を書き添える。
- ユーザーが自分で書いた文は、ユーザーが頼まない限り、書き換えたり消したりしない。
  - 例外: 古い記述と間違った情報は、次の項目のとおり直す（ユーザーが頼んだ範囲に当たる）。
- 古い記述と、間違った情報（いまのコード、採用の ADR、仕様と合わない記述）を見つけたら、作業の途中でも、その場で直す。直したあとで、何をどう直したかをユーザーに伝える。
  - 対象: 仕様書、設計書、実装の記録、ADR、README、コードのコメントと docstring。
  - 理由: 2026-11-04 に、ユーザーが「古い記述は見つけ次第、修正して下さい。特に間違った情報は見つけ次第修正して下さい」と指示した。
  - 例外: どちらが正しいかを Claude が決められない食い違い（2つの文書が違う設計を書いている、ブランチによってコードが違うなど）は、黙って合わせず、ユーザーに伝える。
  - 例外: 試験の記録（日付と条件のついた結果）は、当時の事実なので書き換えない。
  - ADR を直したときは、管理台帳に「追記」か「訂正」の行を足し、adr_lint を実行する。
- 数値には、実測か未計測かを書く。
- 実測の値には、日付と条件を書く。
- 品質の目安には、目標と測り方を、組にして書く（2026-10-16 にユーザーが決めた）。
  - 理由: 測り方がないと、目安を満たしたかを判定できない（arc42 の10章、品質シナリオ: https://docs.arc42.org/section-10/ ）。
- 品質の目安の測り方には、測る区間（何から何までの時間か）、時刻の取り方（動画、システムの記録など）、見る値（中央値、最大）を書く。
  - 例外: 測り方のうち、決まっていないものには「未定」と書く。
- 実装の記録は、`robo_system/docs/implementation/` に置く。
- 書く直前に、書く先のファイルを読み直す。
  - 理由: 別のセッションの Claude やユーザーが、同じ文書を同時に更新していることがある。
