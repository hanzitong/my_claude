# レビューと確認の観点

ADR を書き終えたとき、提案を採用にする前、ユーザーにレビューを頼まれたときに読む。
採用にする前の5つの確認は、SKILL.md の「採用にする前の確認」にある。このファイルには、それ以外の観点をまとめた。
出典は、末尾にまとめた。

## 目次

- レビューの7つの問い
- 書くときによくある誤り
- ADR にするか迷うときの、補助の基準
- レビューする側が陥りやすいこと
- このチームの運用で確かめる点

## レビューの7つの問い

すべての問いに答える。答えは「よい」「直す」「ユーザーに確認」のどれかにし、根拠を添える。

| # | 問い | 主に見る節 |
|---|---|---|
| 1 | ADR に記録するほど重要な問題か | 背景 |
| 2 | 選択肢は、問題を解けるか。有効な方法が欠けていないか | 選択肢 |
| 3 | 観点は、互いに重ならず、漏れがないか | 比較のまとめ |
| 4 | 観点どうしがぶつかるとき、優先順位があるか | 理由（決め手） |
| 5 | 選んだ方法は問題を解くか。理由は納得できるか | 決定、理由 |
| 6 | 良い結果と悪い結果を、できるだけ客観的に書いたか | 選択肢、影響と残る課題 |
| 7 | 実行できる形か。要求までたどれるか。見直すきっかけがあるか | 決定、影響と残る課題、確かめ方 |

言葉づかいも見る。主観的な言葉、曖昧な言葉、逃げ道になる言葉（「場合によっては」「必要に応じて」「なるべく」など）がないかを確かめる。

## 書くときによくある誤り

| 誤り | このチームの書式での見つけ方 |
|---|---|
| 背景が足りない。いまの状況、決める必要が生じた理由、品質の目標がない | 背景に、決める必要が生じた理由と、関係する要求の ID があるか |
| 観点が書かれていない | 比較のまとめに、観点の列があるか |
| 観点を、推したい方法の長所から逆算している | 観点が、背景と要求から説明できるか。推した方法だけが有利になる観点ばかりでないか |
| 見せかけの選択肢（本命をよく見せるための、使えない方法） | 「この方法が適する条件」が、このシステムで実際に起こりうるか |
| 選択肢が1つだけ。目先の影響しか見ていない | 選択肢が2つ以上あるか。長く使ったときの影響があるか |
| 良いことしか書いていない | 採用した方法のデメリットと、悪い影響が書かれているか |
| 宣伝の口調 | 「最適」「圧倒的」などの言葉や、根拠のない主張がないか |
| 採用しなかった理由が足りない | 採用しなかった方法ごとに、選ばなかった理由が分かるか |
| 「決定」が、題名の繰り返し | 「決定」に、決定の種類に応じた表や図があるか |
| 技術の影響しか見ていない | 作業者、システムを動かす人、安全の担当など、技術以外の関係者への影響を考えたか |
| 運用と保守を見ていない | 起動、停止、再起動、ログ、モデルのロードの時間などへの影響を考えたか |
| 設計書の中身を詰め込んでいる | API、関数の一覧、数値の細部が入っていないか。入っていれば、移す先は詳細設計書である |
| 点数で精度を装う | 比較のまとめが、重みづけの点数の合計になっていないか |
| ひな形の使い方がばらばら | 見出しの種類と順番が揃っているか。`adr_lint.py` で確かめる |
| AI の出力を、確かめずに使う | Claude が書いた部分を、ユーザーが見直したか。または、Claude が、この一覧の観点で見直したか |

## ADR にするか迷うときの、補助の基準

まず、SKILL.md の2つの問い（プロセスやスレッドの関係が変わるか。1つのファイルの中で済むか）で判断する。
それで決まらないときに、次の7つを見る。点数の計算には使わない。2つ以上の基準に当たるものは、ADR にするかをユーザーに尋ねる。

| 基準 | 例 |
|---|---|
| 価値やリスクが大きい | 失敗すると、デモが成り立たない |
| 主な関係者の大きな関心事である | 作業者の安全、展示での見え方 |
| 品質の要求が、これまでにない水準である | 推論の待ち時間、着席に気づくまでの時間 |
| 外部への依存がある | 自分たちで直せない機器、モデル、ライブラリ |
| 横断的である | 複数のプロセスに及ぶ |
| 初めての試みである | チームが使ったことのない方式 |
| 以前に問題になった | 以前の試作で困ったこと |

## レビューする側が陥りやすいこと

| 陥りやすいこと | 避け方 |
|---|---|
| 素通し。指摘がほとんどない | 7つの問いのすべてに、根拠を添えて答える |
| 文言だけを直す | 言葉の指摘は最後にまとめ、中身の指摘と分ける |
| 自分が推した案をかばう | 「理由」に、Claude が推したと書いてある方法を、新しい根拠なしにかばわない。レビューする Claude も、推した Claude と同じ偏りを持つ |
| 話が逸れる | 指摘は、対象の ADR の決定に関わるものに絞る |
| 同じ指摘を繰り返す | 同じ指摘は、1か所にまとめて、1回だけ示す |
| 直し方が分からない指摘 | どの節を、どう直すかまで書く |

## このチームの運用で確かめる点

- 状態、関係、更新の記録は、INDEX.md にだけある。ADR のファイルに書いていない。
- 採用した ADR の書き換えは、決定が変わらない場合（追記、訂正）に限る。この範囲の書き換えは、このチームの運用なので、誤りとして指摘しない。
  - 例外: 選んだ方法、決め手、受け入れたデメリットのどれかが変わる書き換えは、置き換え（新しい ADR）に当たらないかを、「ユーザーに確認」として挙げる。
- 「合意」は、ユーザーの発言の引用でしか確かめられない。Claude やエージェントの判断で満たしたことにしない。
- 数値に、実測か未計測かの区別がある。
- 設計書（基本設計書、詳細設計書）の対応する節が、ADR と同じ内容で、ADR の ID が書き添えてある。
- 要約の各部分（場面と課題、得たいこと、採用した方法、選ばなかった方法、受け入れる欠点）の裏づけが、本文の節にある。要約にだけ出てくる主張がない。
  - 例外: 要約は、2026-10-16 から書いている。それより前の ADR に要約がないことは、誤りとして指摘しない。
- 確信の度合いと、その根拠がある。根拠が見込みだけなのに「高」になっていない。確信が低いのに、見直すきっかけがない、という書き漏れがない。
  - 例外: 確信の度合いは、2026-10-16 から書いている。それより前の ADR に確信の度合いがないことは、誤りとして指摘しない。
