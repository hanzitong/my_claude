# ADR の見本

通信方式を決める ADR の見本である。あるロボットのデモのシステムを題材にしている。
見本のあとに、どこが要点なのかの解説がある。

---

```markdown
# ADR-0003: カメラの画像は、推論プロセスが HTTP で1枚ずつ取りに行く

- ID: ADR-0003
- 決定日: 2026-10-07
- 状態と他の ADR との関係: [INDEX.md](INDEX.md) を参照
- 要約: カメラの画像を推論プロセスへ渡し続ける必要があるなかで、作る側と使う側の速さの差に無駄なく対応するために、推論プロセスが HTTP で1枚ずつ取りに行く方法を選び、HTTP のストリームと共有メモリは選ばず、カメラの側から変化を知らせられないことを受け入れる。

## 背景

システムは、人がプロンプトを入力しなくても、周囲を監視し続ける必要があります（REQ-001）。
そのためには、カメラの画像を、推論プロセスへ渡し続ける仕組みが要ります。

カメラプロセスと推論プロセスは、別のプロセスです（ADR-0002）。
この2つの間で、画像をどの方式で、どちらの主導で渡すかを、決める必要がありました。

判断の材料になる事実は、次の通りです。

- カメラは、毎秒30枚程度の画像を撮れる。
- 推論は、1回あたり 0.5 秒から 5 秒かかる（2026-10-05 の検証）。
- 画像は、640 × 480 で、圧縮しない状態で約 0.9 MB ある。
- 2つのプロセスは、同じマシンの上で動く。

画像を作る側（カメラ）が、使う側（推論）より、はるかに速いです。
推論プロセスが使える画像は、撮影されたうちの数十枚に1枚です。

## 選択肢

### A. 推論プロセスが、HTTP で1枚ずつ取りに行く（採用）

推論プロセスが、1回の推論ごとに、カメラプロセスへ HTTP で画像を要求します。

- メリット
  - 遅い側の推論プロセスが、自分のペースで取りに行く。処理しきれない画像が溜まらない。
  - 使わない画像を、変換も転送もしない。
  - 推論プロセスの側は、要求を1回送るだけで済む。画像を読み続けるスレッドが要らない。
  - コマンドやブラウザから、手で1枚だけ取得して確かめられる。
- デメリット
  - 1回ごとに、圧縮と、要求と応答のやりとりが入る（実測で約3ミリ秒）。
  - カメラプロセスの側から、「変化があった」と知らせることができない。

### B. カメラプロセスが、HTTP のストリームで画像を流し続ける

推論プロセスが1回だけ要求し、そのあとはカメラプロセスが、撮影した画像を流し続けます。

- メリット
  - 1回ごとの、要求のやりとりがなくなる。
  - 同じストリームを、人がブラウザで映像として確認できる。
- デメリット
  - 推論している間に流れてきた画像が、通信のバッファに溜まる。次に読むと、古い画像が手に入る。
  - それを避けるには、推論プロセスの側に、読み続けて最新の1枚だけを残すスレッドが要る。
  - 毎秒30枚を圧縮して送り、そのほとんどを捨てる。
- この方法が適する条件
  - すべての画像を使う処理（毎フレームの検出など）が加わったとき。

### C. 共有メモリに最新の画像を置き、推論プロセスが読む

カメラプロセスが、最新の画像を共有メモリに書き続けます。推論プロセスは、必要なときに読みます。

- メリット
  - 圧縮も、通信も要らない。画質が落ちない。
  - 遅い側が自分のペースで読める点は、A と同じである。
- デメリット
  - 書いている最中に読まないための排他を、プロセスをまたいで設計する必要がある。
  - 同じマシンの上でしか使えない。
  - 手で確かめる手段を、別に用意する必要がある。
  - チームが、この方式に慣れていない。
- この方法が適する条件
  - 画像が大きくなる、または頻度が上がって、圧縮と転送の時間が推論の時間に対して無視できなくなったとき。

### 比較のまとめ

| 観点 | A. HTTP で取りに行く | B. HTTP のストリーム | C. 共有メモリ |
|---|---|---|---|
| 画像の新しさ | 常に新しい | 読み捨てを続けないと古くなる | 常に新しい |
| 使わない画像の処理 | なし | 毎秒30枚を圧縮して送る | 書き込みだけ |
| 1回あたりの遅れ | 約3ミリ秒（実測） | 要求のぶんだけ短い（未計測） | ほぼなし（未計測） |
| 推論プロセスの側の仕組み | 要求を1回送る | 読み続けるスレッドが要る | 排他の設計が要る |
| 別のマシンへの移行 | できる | できる | できない |
| 手での確かめやすさ | 確かめやすい | ブラウザで見られる | 手段を別に作る |
| チームの習熟 | 慣れている | 慣れていない | 慣れていない |

## 決定

A を採用します。

| どこから | どこへ | 方式 | 働きかける側 | 渡すもの | 相手が止まっているとき |
|---|---|---|---|---|---|
| 推論プロセス | カメラプロセス | HTTP（要求と応答） | 推論プロセス | 画像1枚 | 要求がエラーになる。次の周期に、もう一度要求する |

カメラプロセスの側から、推論プロセスへ、画像や通知を送ることはしません。

## 理由

- 決め手は、作る側と使う側の速さの差です。カメラは毎秒30枚、推論は1回に 0.5 秒以上なので、遅い側が取りに行く形が、最も単純で無駄がありません。
- 1回あたりの遅れ（約3ミリ秒）は、推論の時間（0.5 秒以上）に対して1%未満です。C で遅れをなくしても、全体はほとんど速くなりません。
- ユーザーの決定です（2026-10-07）。「今回は、VLM が常にカメラプロセスに要求を出し続ける構成としましょう」
- 前提: 2つのプロセスが同じマシンの上で動き、画像が 640 × 480 であること。
- 確信の度合い: 高。1回あたりの遅れと、推論の時間を、どちらも実測している。

## 影響と残る課題

- カメラプロセスは、要求が来た時点の最新の画像を返せる必要があります。カメラプロセスの中のスレッドの分け方は、別の ADR で決めます。
- 画像が大きくなった場合、または頻度を上げる場合は、C を新しい ADR として検討します。
- 毎フレームを使う処理が加わった場合は、B を新しい ADR として検討します。

## 確かめ方

- 守られているか: カメラプロセスから推論プロセスへの送信がないことを、コードの検索で確かめます。
- 効いているか: 画像の撮影から推論の開始までの遅れを測り、実装の記録に、日付と条件をつけて残します。
```

## 解説

**題名が、決定そのものになっている。**
「画像の受け渡しについて」ではなく、「推論プロセスが HTTP で1枚ずつ取りに行く」と書いている。
題名だけで、方式（HTTP）と、向き（推論プロセスが取りに行く）が分かる。

**アーキテクチャレベルの決定だけを書いている。**
決めているのは、2つのプロセスの間の通信方式と、働きかける向きである。
画像の圧縮形式や、要求を出す間隔の秒数は、書いていない。

**背景に、判断の材料になる事実がある。**
「毎秒30枚」と「1回に 0.5 秒から 5 秒」という2つの数字が、選択肢を比べる土台になっている。
事実がないと、メリットとデメリットが「速い」「遅い」という感想になってしまう。

**選択肢が、実際に選べる方法である。**
B と C は、どちらも現実に成り立つ方法である。読み手が「ストリームではだめなのか」「共有メモリのほうが速いのでは」と思うことを見越して、挙げている。

**採用した方法にも、デメリットを書いている。**
A の「カメラプロセスの側から、『変化があった』と知らせることができない」は、のちに問題になりうる点である。隠さずに書いている。

**同じ観点で比べている。**
「比較のまとめ」の表で、3つの方法を、同じ7つの観点で並べている。
測った値には「実測」、測っていない値には「未計測」と書いて、区別している。

**採用しなかった方法に、「適する条件」がある。**
ユーザーが B と C を選ばなかったのは、劣っているからではなく、いまの条件に合わないからである。
条件が変わったときに見直せるように、その条件を書いている。

**理由が、決め手に絞られている。**
メリットを並べ直すのではなく、「速さの差」と「1%未満の遅れ」という、決定を分けた点を書いている。
誰が決めたのかと、もとになった発言も書いている。

**1つの決定だけを書いている。**
「カメラプロセスの中のスレッドの分け方」は、関係はあるが、別の決定である。
この ADR には書かず、「別の ADR で決める」と残る課題に書いている。

**確かめ方が、確かめられる形で書かれている。**
「守られているか」は、コードを検索すれば確かめられる。「効いているか」は、何を測るかが決まっている。
測った結果は ADR に書かず、実装の記録に残す。ADR は決定の記録であり、試験の記録ではないためである。

**要約だけで、決定の全体が分かる。**
場面と課題、得たいこと、採用した方法、選ばなかった方法、受け入れる欠点が、1文に入っている。
どの部分も、本文の節に裏づけがある。要約にだけ出てくる主張はない。

**確信の度合いに、根拠がある。**
「高」とした根拠は、遅れと推論の時間を実測していることである。見込みや仮定に頼っているなら「低」にする。
