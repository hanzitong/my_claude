# ADR の書き方

ADR は、アーキテクチャレベルの決定を、1つの決定につき1つのファイルで残す記録である。

ADR の読み手は、あとからこの構成を見て「なぜこうなっているのか」と思う人である。
その人が知りたいのは、決定そのものよりも、**ほかにどんな方法があり、なぜそれを選ばなかったのか**である。
決定だけが書かれた記録は、コードを読めば分かることを繰り返しているにすぎない。
このスキルの決まりは、どれも「選ばなかった方法と、その理由を残す」ためにある。

決めるのはユーザーである。Claude は、選択肢を整理して、比べて、記録する。
ユーザーが決めていないことを、決まったこととして書かない。

## ADR に書くこと、書かないこと

ADR に書くのは、**アーキテクチャレベルの決定だけ**である。
細かな話まで ADR にすると、数が増えて、本当に大事な決定が埋もれる。
細かな話を ADR にすると、その話が変わるたびに ADR を書き直すことにもなり、記録を続けられなくなる。

書くこと（アーキテクチャレベルの決定）

| 種類 | 決める内容 |
|---|---|
| プロセスの分け方 | システムをどんなプロセスに分けるか。それぞれが何を担当するか |
| プロセス間の通信方式 | HTTP、ソケット通信、共有メモリ、発行と購読などの、どれを使うか。どちらの側から働きかけるか |
| スレッドの分け方 | 1つのプロセスの中に、どんなスレッドを持つか。それぞれが何を担当するか |
| 状態の持ち方 | プロセスやシステムに、状態をいくつ持たせるか。それぞれの状態は、どんな目的を持つか。どこが状態を管理するか |
| 役割の置き場所 | ある判断やデータを、どのプロセスが受け持つか |

書かないこと（細かな話）

- 数値の調整（周期の秒数、回数、枚数、タイムアウトなど）
- データの形式の細部（画像の圧縮形式、JSON の項目名など）
- エラー処理の細部（何秒待ってやり直すか、どのエラーを返すかなど）
- 関数、変数、ファイル、ディレクトリの名前
- 関数、変数、ファイル、ディレクトリの置き場所
- 関数を1つ足す、機能を1つ削る、といった個別の変更
- プロンプトの文面
- モックの中身
- 1つのファイルの中だけで完結する、実装の工夫

### 判断の例

| 決定 | ADR に書くか | 理由 |
|---|---|---|
| カメラ、推論、ロボット動作を、別々のプロセスに分ける | 書く | プロセスの分け方である |
| プロセスの間を、HTTP でつなぐ | 書く | 通信方式である |
| 画像は、使う側のプロセスが取りに行く。送る側からは流さない | 書く | 通信の向きである。変えると、両方のプロセスの作りが変わる |
| カメラを読み続けるスレッドと、要求に応えるスレッドに分ける | 書く | スレッドの分け方である |
| システムの状態を「監視」「対応中」「動作中」の3つにする | 書く | 状態の持ち方である |
| 状態は、推論を行うプロセスが管理する | 書く | 役割の置き場所である |
| 監視の周期を1秒にする | 書かない | 数値の調整である。定数を1つ変えれば済む |
| 画像を JPEG にして返す | 書かない | データの形式の細部である |
| 「何もしない」関数を1つ用意する | 書かない | 関数を1つ足す話である |
| 起動時に、最初の20枚を読み捨てる | 書かない | 1つのファイルの中で完結する工夫である |
| コードを、別のディレクトリにまとめ直す | 書かない | 置き場所の話である。動いているときの構成は変わらない |

迷ったときは、次の2つの問いで判断する。

- この決定を変えると、**プロセス同士やスレッド同士の関係**が変わるか。変わるなら、ADR に書く。
- 1つのファイルの中を直すだけで済むか。済むなら、ADR には書かない。

それでも判断がつかないときは、`references/review-checklist.md` の「ADR にするか迷うときの、補助の基準」を見たうえで、書く前にユーザーに尋ねる。

### 細かな話が出てきたとき

細かな話は、捨てるのではなく、設計書か、コードのコメントに書く。

あわせて、細かな話の裏に、アーキテクチャレベルの問いが隠れていないかを考える。
たとえば「周期を何秒にするか」は細かな話だが、「誰がタイミングを決めるのか（送る側か、使う側か）」は通信方式の決定である。
隠れている問いがまだ決まっていなければ、そちらを ADR の題材としてユーザーに示す。

## 文書の役割分担

ADR は、仕様書、設計書、管理台帳と組にして使う。それぞれ、答える問いが違う。

- **仕様書**が答える問い:「システムは、何を満たすべきか」
- **設計書**が答える問い:「いま、どういう設計になっているか」
- **ADR**が答える問い:「なぜ、その設計にしたのか。ほかにどんな方法があったのか」
- **管理台帳**が答える問い:「どの決定が、いま有効か。いつ、何が変わったか」

| 文書 | 書くこと | 書かないこと |
|---|---|---|
| 仕様書 | システムが何を満たすべきか。外から見た振る舞い、機能、性能、制約 | 内部の構造（プロセス、スレッド、通信方式など）。それらは設計書に書く |
| 設計書 | いま有効な設計の全体。プロセス、通信、状態、スレッド、関数の一覧。数値や形式などの細かな話。まだ決めていないこと | 以前の設計。採用しなかった方法。決定に至った経緯 |
| ADR | アーキテクチャレベルの決定。その選択肢、比較、理由 | 細かな話。設計の全体の説明 |
| 管理台帳（INDEX.md） | ADR の状態、ADR 同士の関係、更新の記録 | 決定の中身 |
| 判断材料のファイル（あれば） | 実行環境、実測の結果、懸念点 | 設計そのもの |

設計書と ADR の場所は、プロジェクトの `CLAUDE.md` に従う。

仕様書と設計書が、基本と詳細に分かれているプロジェクトでは、それぞれの文書と ADR を、次のように対応させる。

| 文書 | 定義すること | ADR との関係 |
|---|---|---|
| 基本仕様書 | 何を満たすべきか（全体）。目的、機能の一覧、動作環境、制約 | ADR の「背景」が参照する。ADR の決定は書かない |
| 詳細仕様書 | 何を満たすべきか（機能ごと）。振る舞い、状態、数値の目安 | ADR の「背景」が参照する。状態の一覧のように、振る舞いとして外から見えるものは、ここに書く |
| 基本設計書 | どう実現するか（全体の構造）。プロセスの構成、通信方式、スレッドの構成、状態の管理 | **ADR の決定が、主に対応する文書である。** 決定に当たる箇所に、ADR の ID を書き添える |
| 詳細設計書 | どう実現するか（内部の作り）。URL、データの形、関数、処理の手順、数値 | ADR にしない細かな話を書く |

ある情報を、仕様書と設計書のどちらに書くかは、「外から見て分かる振る舞いか、内部の構造か」で決める。
同じ情報を、2つの文書に重ねて書かない。片方に書いて、もう片方からは参照する。

### 設計書には、古い情報を残さない

設計書は、「いま、どうなっているか」を知るために読むものである。
以前の設計と、いまの設計が混ざっていると、読み手は、どれが有効なのかを判断できない。

- 設計が変わったら、設計書の該当する箇所を、新しい内容に書き換える。古い内容を、取り消し線や「以前は〜だった」という形で残さない。
  - 理由: 以前の設計と、変えた理由は、ADR に残る。古い ADR は、管理台帳で「置き換え済み」になるので、新旧は管理台帳でたどれる。
  - 例外: ユーザーが自分で書いた文は、ユーザーに頼まれた範囲だけを書き換える。
- 設計書以外の文書（全体の説明、要求の一覧など）に、以前の設計の説明が残っていたら、削除する。
  - 理由: 設計の説明は、いまの設計書に書いてあれば足りる。
  - 例外: まだ有効で、ほかのどこにも書かれていない情報（実測の結果など）は、削除せずに残す。削除する前に、そうした情報が混ざっていないかを確かめる。

### 設計書と ADR を、揃えておく

- **設計書から、ADR を参照する。** アーキテクチャレベルの決定に当たる箇所には、「（ADR-0003）」のように、ID を書き添える。
  - 理由: 読み手が、理由を知りたいときに、ADR へたどれるようにするためである。
- **ADR を書いたら、設計書の対応する節を、同じ内容に更新する。**
  - 理由: ADR だけを書いて設計書を直さないと、設計書が古いまま残る。

  対応する節は、次の表のとおりである。

  | ADR の決定の種類 | 設計書（基本設計書）の、対応する節 |
  |---|---|
  | プロセスの分け方 | プロセスの構成 |
  | プロセス間、スレッド間の通信方式 | 通信、API の一覧 |
  | スレッドの分け方 | スレッドの一覧、共有するデータ |
  | 状態の持ち方 | 状態の一覧、移り変わり |
  | 役割の置き場所 | 該当するプロセスの役割 |

- **ADR を置き換えたら、設計書を新しい内容に書き換える。** 書き添えた ID も、新しい ADR のものに直す。
- **設計書の「まだ決めていないこと」と、ADR の「影響と残る課題」を、揃える。** 決まったことは、設計書の「まだ決めていないこと」から消す。
- **ADR に書かない細かな話は、設計書に書く。**
- **コードのコメントに ADR の ID を書いている場合は、ADR を置き換えたり削除したりしたときに、あわせて直す。**

設計書の中に、ユーザーが自分で書いた部分があるときは、その文を勝手に書き換えたり消したりしない。ユーザーに頼まれた範囲で、書き足すか、直す。

## 必ず書くこと

次の3つが揃っていないものは、ADR として成り立たない。

- **ほかの実現方法**: 採用した方法のほかに、少なくとも1つ、実際に成り立つ別の方法を書く。
- **比較したメリットとデメリット**: それぞれの方法について、ほかの方法と比べたときのメリットとデメリットを書く。
- **理由**: なぜその方法を選んだのかを書く。

### 選択肢の書き方

- **実際に選べる方法だけを挙げる。** 採用した方法を良く見せるためだけの、明らかに劣る方法は挙げない。読み手が「なぜあの方法にしなかったのか」と思いそうな方法を、優先して挙げる。
- **「いまのまま」も選択肢に含める。** 何かを変える決定では、変えない場合のメリットとデメリットも書く。
- **会話に出た方法は、すべて含める。**
  - 理由: ユーザーが口にした方法を落とすと、あとで「あれは検討したのか」が分からなくなる。
- **採用した方法のデメリットを、必ず書く。**
  - 理由: デメリットのない方法はない。デメリットを書いていなければ、検討が足りていない。
- **同じ観点で比べる。** 観点（速さ、扱えるデータの大きさ、仕組みの単純さ、障害が起きたときの影響、習得のしやすさなど）を先に決めて、すべての方法をその観点で書く。観点ごとの比較を、表にまとめるとよい。
  - 理由: ある方法では速さを、別の方法では単純さだけを書く、という書き方では比べられない。
- **採用しなかった方法が、どんな条件なら適するかを書く**（例: 「入力が複数になったら、この方法を検討する」）。
  - 理由: 条件を書いておくと、見直すきっかけが分かる。
- **数値は、測った値か、見込みの値かを区別する。** 測っていない値には「未計測」と書く。決め手になる数値は、できれば測ってから書く。

決定の種類ごとの、よくある選択肢と、比べる観点は、`references/decision-types.md` にまとめてある。
選択肢を洗い出すときに読む。

### 理由の書き方

理由には、次のことを書く。

- **決め手**: どの観点が、決定を分けたのか。メリットをすべて並べ直すのではなく、決め手になった点を書く。
- **誰が決めたか**: ユーザーか、Claude か。ユーザーの発言がもとになっている場合は、その発言を引用して、日付を添える。Claude が選んだ場合や、ユーザーの指定を具体化するために補った場合は、そのことを書く。
- **前提**: その決定が成り立つ条件。関係する要求に ID があれば、その ID で参照する。
- **確信の度合い**: 高、中、低のどれかと、その根拠。
  - 理由: 確信の低い決定は、あとで見直す候補になる。
  - 例外: 確信の度合いは、2026-10-16 から書いている。それより前の ADR に確信の度合いがないのは、誤りではない。

  | 度合い | 目安 |
  |---|---|
  | 高 | 実測、試作、すでに動いている実績で、うまくいくことを確かめた |
  | 中 | 根拠はあるが、この構成では、まだ確かめていない |
  | 低 | 見込みや仮定に頼っている。ひとまずの決定である |

  ユーザーの発言に、確信の度合いを示す言葉（「ひとまず」「たぶん」など）があれば、その言葉が示す度合いに従う。なければ、Claude の見立てとして書き、そう添える。
  確信が低い決定は、「影響と残る課題」に、何が分かったら見直すかを必ず書く。

理由が分からないときは、推測で埋めない。「指定なし」「確認が必要」と書いて、ユーザーに尋ねる。
もっともらしい理由を作って書くと、読み手はそれを事実として受け取る。分からないと書いてあるほうが、役に立つ。

## 決定の種類ごとに、「決定」に入れるもの

「決定」の節は、採用した方法の名前だけで終わらせない。構成が分かるように、次のものを入れる。

| 種類 | 「決定」に入れるもの |
|---|---|
| プロセスの分け方 | プロセスの一覧の表（名前、担当すること、持っているもの）。プロセスと、そのつながりを示す図 |
| プロセス間の通信方式 | つながりごとの表（どこからどこへ、方式、働きかける側、渡すもの）。相手が止まっているときの扱い |
| スレッドの分け方 | スレッドの一覧の表（名前、担当すること、始まるとき、終わるとき）。スレッドの間で共有するデータと、その守り方 |
| 状態の持ち方 | 状態の一覧の表（名前、目的、その状態で行うこと）。移り変わりの表（いまの状態、きっかけ、行うこと、次の状態）。状態を管理する場所 |
| 役割の置き場所 | その役割を受け持つプロセス。ほかのプロセスが、その判断やデータを知る方法 |

それぞれの詳しい書き方は、`references/decision-types.md` にある。

## ファイルの置き場所と名前

- 置き場所は、プロジェクトの `CLAUDE.md` が指定するディレクトリにする。指定がなければ、ユーザーに尋ねる。
- ファイル名は `ADR-<4桁の連番>-<英語の短い名前>.md` にする（例: `ADR-0003-vlm-pulls-frames-from-camera.md`）。
- **1つの決定につき、1つのファイルにする**（例: 「プロセスを分ける」と「その間を HTTP でつなぐ」は、別々に変えられるので、2つの決定である）。
  - 理由: 片方の決定だけを変えたときに、もう片方の記録まで書き直さずに済む。
- **番号を決める前に、ディレクトリの中を一覧して、いま使われている最大の番号を確かめる。** 覚えている番号をそのまま使わない。
  - 理由: 別の作業で、すでに新しい ADR が足されていることがある。
- 番号は、連番で振る。削除した ADR の番号は、使い直さない。

## ADR の構成

ひな形は `assets/adr-template.md` にある。見出しは、次の5つを、この順で使う。
6つ目の「確かめ方」は任意である。書くときは、最後に置く。

| 見出し | 書くこと |
|---|---|
| 背景 | 決める必要があったこと。判断の材料になった事実。関係する要求 |
| 選択肢 | 実現方法ごとの、メリットとデメリット。採用した方法を示す「（採用）」の印 |
| 決定 | 採用した方法の、具体的な内容。その内容を示す表と図 |
| 理由 | 決め手、誰が決めたか、前提、確信の度合い |
| 影響と残る課題 | この決定によって必要になること。まだ決まっていないこと。見直すきっかけ |
| 確かめ方（任意） | 決定が守られているか、狙いどおりに効いているかを確かめる手段 |

- 題名は、決定の内容そのものにする（例: 「通信方式について」ではなく、「プロセスの間を HTTP でつなぐ」と書く）。
  - 理由: 読み手が、題名だけを読んで、何を決めたのかが分かるようにするためである。
- 冒頭の行は、ID、決定日、状態と他の ADR との関係、要約の4つにする。
  - 例外: 要約は、2026-10-16 から書いている。それより前の ADR に要約がないのは、誤りではない。
- 「状態と他の ADR との関係」の行には、管理台帳（INDEX.md）への案内だけを書く。状態（採用、置き換え済みなど）と、ほかの ADR との関係そのものは、ADR のファイルには書かず、管理台帳にだけ書く。

全体の見本は、`references/example.md` にある。初めて書くときや、書き方に迷ったときに読む。

### 要約の書き方

要約は、決定の全体を1文にまとめたものである。要約の形は、Y-statement と呼ばれる書き方を、この書式に当てはめたものである。
題名は「何を決めたか」だけを示す。要約は、なぜその方法にしたか、何と比べたか、何を受け入れたかまでを、1文で示す。

```
- 要約: 〈場面と課題〉に対し、〈得たいこと〉のために〈採用した方法〉を選び、〈選ばなかった方法〉は選ばず、〈受け入れる欠点〉を受け入れる。
```

- 要約は、本文を書き終えてから書く。要約の各部分は、本文の節にある内容をまとめたものにする。要約にだけ出てくる主張を作らない。

  | 要約の部分 | 裏づけになる節 |
  |---|---|
  | 場面と課題 | 背景 |
  | 得たいこと | 理由の決め手 |
  | 採用した方法 | 決定 |
  | 選ばなかった方法 | 選択肢 |
  | 受け入れる欠点 | 選択肢のデメリット、影響と残る課題 |

- 状態が「提案」のときは、「選び」を「提案し」に替える。
- 選ばなかった方法が多いときは、読み手が「なぜそうしなかったのか」と思いそうなものを挙げる。

### 確かめ方の書き方

確かめ方は、MADR 4.0 の Confirmation に当たる節である。決定を記録して終わりにせず、守られているか、効いているかを確かめられるようにする。

- 確かめる手段があるときだけ書く。書かないときは、節ごと省く。
- 次の2つを分けて書く。
  - **守られているか**: 決定に反する作りになっていないかを、何で確かめるか（例:「プロセスの間の呼び出しが HTTP だけであることを、コードの import と URL の検索で確かめる」）。
  - **効いているか**: 決定の狙いが果たされているかを、何を測って、何と比べて確かめるか。仕様書の品質の目安に ID があれば、測った値を、その ID の目安と比べる（例:「画像の撮影から推論の開始までの遅れを測り、品質の目安（QLT-xxx）と比べる」）。
- 確かめた結果は、ADR に書かない。結果は実装の記録に、日付と条件をつけて書く。
- 自動の検査（テストやスクリプト）を作るのは、ユーザーが頼んだときだけにする。
- ADR には、確かめる性質と、手段と、結果の記録先を書く。

### ADR には、最終形だけを書く

ADR のファイルには、**いまの内容だけ**を書く。変更の経緯は、書かない。
読み手が知りたいのは、背景、設計の根拠、選択肢の比較、解説である。「いつ、どこを書き足したか」が混ざると、いまの内容が読み取りにくくなる。

- 内容を足すとき、直すときは、該当する箇所を、そのまま書き換える。
- 「追記」「訂正」という印や、書き足した日付を、本文につけない。
- 「以前は〜と書いていた」「はじめは〜だった」「その後〜に変えた」という書き方をしない。
- ほかの ADR で決まったことは、「〜です（ADR-0007）」と、いまの事実として書く。「この時点では未決定だった」とは書かない。
- 変更の経緯を残したいときは、管理台帳の更新の記録に書く。

**ただし、内容の確かさを示すメモは、残す。** 変更の経緯とは違い、読み手が、その内容をどこまで信じてよいかを判断するのに要るためである。

| 残すメモ | 例 |
|---|---|
| 仮であること | 「仮の値である」「仮の処置である」「いったん、〜とする」 |
| 実装の状況 | 「今回は実装しない」「コードには、コメントだけがある」 |
| 誰が決めたか | 「ユーザーの決定である（日付と発言）」「Claude が補った」 |
| 分かっていないこと | 「指定なし」「比較していない」「確認が必要」「未計測」 |

決定した日や、発言の日、測った日は、根拠の一部なので、書いてよい。書かないのは、文書を直した日である。

## 管理台帳（INDEX.md）

ADR の**状態**、**ADR 同士の関係**、**更新の記録**は、管理台帳にだけ書く。
2か所に書くと、片方だけを直して食い違うためである。どの ADR がいま有効か、いつ何が変わったかは、管理台帳を見れば分かるようにする。

管理台帳には、次の4つを置く。

| 節 | 内容 |
|---|---|
| 一覧 | ID、題名、状態、決定日 |
| 削除した ADR | 削除した番号と、書いてあった内容、削除した理由 |
| 関係 | 元の ID、関係の種類、先の ID、補足 |
| 更新の記録 | 日付、ID、種類（新規、追記、訂正、置き換え、削除）、内容 |

一覧は、ID の順に並べる。更新の記録には、ADR に手を入れるたびに、1行足す。

ADR のファイルには、最終形だけを書く。変更の経緯が残るのは、更新の記録だけである。

管理台帳がまだなければ、`assets/index-template.md` をもとに作る。
状態の種類、関係の種類、更新の記録の種類は、そのひな形に書いてある。

## 手順

### 書く前に、どこに書くかを判断する

ユーザーから決定や指示を受けたら、すぐに新しい ADR を書き始めない。まず既存の ADR を読んで、受けた決定や指示が、次のどれに当たるかを判断する。
毎回新しい ADR を足していくと、同じ話が複数の ADR に散らばって、どれが有効なのかが分からなくなる。

| 当てはまる場合 | 行うこと |
|---|---|
| まだどの ADR にも書かれていない、アーキテクチャレベルの決定である | 新しい ADR を書く |
| 既存の ADR の決定を、別の方法に変える決定である | 新しい ADR を書いて、古い ADR を置き換える |
| 既存の ADR で「未決定」「確認が必要」としていたことが、決まった | アーキテクチャレベルなら、新しい ADR を書き、もとの ADR の該当する箇所は、決まった内容に書き換える。アーキテクチャレベルでなければ、既存の ADR を書き換えるだけにする |
| 既存の ADR の決定から、そのまま導かれることの確認である | 既存の ADR の該当する箇所に、書き入れる。決定そのものは変えない |
| 既存の ADR に書いた内容が、単に誤っていた（決定を変えるわけではない） | 既存の ADR を直接直す。直した印は、ADR の中に残さない。同じ誤りを引き継いでいる、ほかの ADR も直す |
| アーキテクチャレベルではない、細かな話である | ADR には書かない。設計書に書く |

どの場合でも、ADR は最終形に書き換える（「ADR には、最終形だけを書く」）。設計書も、いまの内容に合わせて直す。
判断した結果と、その理由は、ユーザーに伝える。

### 新しい決定を記録するとき

1. 管理台帳を読む。関係する ADR があれば、そのファイルも読む。
2. その決定が、アーキテクチャレベルかどうかを確かめる。細かな話であれば、ADR にはせず、そのことをユーザーに伝える。
3. 1つの決定になっているかを確かめる。2つ以上が混ざっていれば、分ける。
4. ほかの実現方法を洗い出す。`references/decision-types.md` を読んで、抜けている方法がないかを確かめる。
5. 理由が分かっているかを確かめる。分かっていなければ、書く前にユーザーに尋ねる。
6. ディレクトリを一覧して、次の番号を決める。
7. ADR のファイルを書く。
8. 管理台帳の一覧と関係に、行を足す。更新の記録にも、「新規」の行を足す。
9. 設計書の対応する節を、決定の内容に合わせて直す。ADR の ID を書き添える。「まだ決めていないこと」から、決まった項目を消す。
10. ユーザーに、書いた ADR、直した設計書の箇所、Claude が補った部分、確認が必要な点を伝える。

### 決定を変えるとき

ユーザーが、採用した方法そのものを、別の方法に変えると決めたときは、古い ADR を書き換えずに、新しい ADR で置き換える。古い ADR は、その決定の最終形として、そのまま残る。

1. 新しい番号で、新しい ADR を書く。新しい ADR には、古い ADR から引き継ぐ内容と、変える内容を、はっきり書く。古い ADR の方法は、選択肢の1つとして挙げる。
2. 管理台帳の関係に、「新しい ADR が、古い ADR を置き換える」の行を足す。
3. 管理台帳の一覧で、古い ADR の状態を「置き換え済み」に変える。更新の記録に、「置き換え」の行を足す。
4. 設計書の該当する箇所を、新しい内容に書き換える。古い内容は残さない。書き添えた ID を、新しい ADR のものに直す。

採用した方法を変えない書き換え（誤字の修正、事実の誤りの訂正、分かった理由の書き入れ、ほかの決定に合わせた手直し）では、既存のファイルを直接直す。
内容を書き足したり書き換えたりしたときは、管理台帳の更新の記録に、「追記」の行を足す。誤りを直したときは、「訂正」の行を足す。ADR のファイルの中には、印を残さない。

### ADR を削除するとき

ADR は、ふつうは削除しない。決定が無効になったときは、状態を「置き換え済み」か「廃止」にして残す。
削除するのは、アーキテクチャレベルではない細かな話を ADR にしてしまっていた場合で、ユーザーが削除を指示したときだけである。

1. 削除する前に、内容のうち残すべきものを、設計書に移す。
2. ADR のファイルを削除する。
3. 管理台帳の一覧から行を消す。その ADR が出てくる関係の行も、すべて消す。
4. 管理台帳に、削除した番号と、書いてあった内容を記録する。更新の記録に、「削除」の行を足す。
5. ほかの ADR、コードのコメント、説明のファイルに、削除した番号への参照が残っていないかを検索して、直す。

### アーキテクチャの相談を受けたとき

相談の段階では、ADR を書かない。ユーザーが決めてから書く。
ただし、相談への答えは、そのまま ADR にできる形で組み立てる。ユーザーが決めたときに、すぐ記録できるようにするためである。

1. 答えを組み立てる前に、管理台帳を読む。これから示す答えが、状態が「採用」の ADR と矛盾しないかを確かめる。
2. 観点を先に決めてから、選択肢を同じ観点で比べて示す。推したい方法の長所から、観点を逆算しない。ロボットのシステムで抜けやすい観点（データが古くないか、通信が切れたときに安全側に倒れるか、周期が乱れないかなど）は、`references/decision-types.md` にある。Claude の考えも、理由をつけて示す。
3. 答えが、状態が「採用」の ADR を変えるものであれば、そのことをユーザーに伝える。
4. ユーザーが決めたら、その内容を ADR にするかを、ユーザーに尋ねる。ユーザーが ADR にすると答えたら、記録する。

## 採用にする前の確認

状態を「採用」にする前に、次の5つを確かめる。新しい ADR を「採用」で書くときも、「提案」を「採用」に変えるときも同じである。
この5つは、ecADR と呼ばれる決定の完了の条件（Evidence、Criteria、Agreement、Documentation、Realization/Review）を、この書式に当てはめたものである。

| 項目 | 確かめること | ADR のどこで確かめるか |
|---|---|---|
| 根拠 | 選んだ方法がうまくいくと考える根拠（計測、試作、すでに動いている実績など）がある。数値に、実測か未計測かの区別がある | 背景、理由（確信の度合い） |
| 比較 | 実際に選べる方法を2つ以上、同じ観点で比べた | 選択肢、比較のまとめ |
| 合意 | ユーザーが決めた | 理由に、ユーザーの発言の引用と日付がある。Claude やエージェントの判断では満たせない |
| 記録 | 管理台帳と設計書を、ADR に揃えた | 管理台帳の一覧、関係、更新の記録。基本設計書と詳細設計書の対応する節 |
| 実現と見直し | いつ実装するか、何で確かめるか、どうなったら見直すかが分かる | 影響と残る課題、確かめ方 |

満たしていない項目があれば、状態は「提案」のままにする。足りないものを、ユーザーに伝える。

## 書き終えたあとの確認

- アーキテクチャレベルの決定である。細かな話が混ざっていない。
- 1つのファイルに、1つの決定だけが書かれている。
- 題名だけを読んで、何を決めたのかが分かる。
- 採用しなかった方法が、少なくとも1つ書かれている。それは、実際に選べる方法である。
- すべての方法に、メリットとデメリットの両方が書かれている。同じ観点で比べている。
- 理由に、決め手と、誰が決めたのかが書かれている。
- 推測で埋めた理由がない。分からない部分には「指定なし」「確認が必要」と書いてある。
- 測っていない数値に、「未計測」と書いてある。
- 「決定」に、種類に応じた表や図が入っている。
- 番号が、ほかの ADR と重なっていない。
- 管理台帳の一覧、関係、更新の記録を、更新した。
- 設計書の対応する節が、ADR と同じ内容になっている。ADR の ID を書き添えた。
- 設計書に、以前の設計の説明が残っていない。
- 状態と関係を、ADR のファイルの中に書いていない。
- ADR のファイルに、変更の経緯（「追記」「訂正」の印、書き足した日付、「以前は〜だった」）が書かれていない。
- 仮の値、仮の処置、未実装、「指定なし」などのメモは、残っている。
- 検査のスクリプトを Claude が自分で実行し、問題がないことを確かめた（`python3 ~/.claude/hooks/adr_lint.py <プロジェクトのディレクトリ>`）。
  - 理由: 社内の設定でフックが動かないので、Claude Code は検査を自動では実行しない。
- 観点を、推したい方法の長所から逆算していない。観点は、背景と要求から説明できる。
- 「決定」が、題名の繰り返しになっていない。
- 冒頭に、要約が1文で書かれている。要約の各部分の裏づけが、本文の節にある。
- 理由に、確信の度合いと、その根拠が書かれている。確信が低い決定には、見直すきっかけが書かれている。
- 「影響と残る課題」を書くときに、技術以外の関係者（作業者、システムを動かす人、安全の担当など）への影響も考えた。
- 確かめ方を書いた場合、守られているかと、効いているかが分かれている。確かめた結果は書いていない。
- Claude が書いた部分を、`references/review-checklist.md` の観点で見直した。

大きな決定では、ユーザーに `/adr-review`（adr-reviewer エージェントによるレビュー）を勧める。
