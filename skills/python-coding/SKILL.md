# Python のコーディング

このスキルは、Python のコードを書く手順と、点検の項目をまとめたものである。
決まりの中身（理由、例、例外）は、下の表のルールファイルに書いてある。このスキルとルールファイルが食い違うときは、ルールファイルを正とする。

ユーザーが特に重く見ているのは、次の3つである（2026-11-03）。

- 名前の付け方を、厳しく守る。目的は、可読性である。ユーザーが「命名規則」と言うときは、特に `~/.claude/rules/python-descriptive-names.md` の冒頭に書いた3つを指す。
- 型ヒントを、必ず付ける。
- すべての関数とクラスに docstring を書き、その **目的** を明記する。

## 書く前

1. プロジェクトのルールが、コードを書き換えてよい場合を決めているときは、それに従う。
2. 周りのコードを読み、コメントの量、区切りの見出し、docstring の形を、周りのコードに合わせる。
   - 例外: 名前、型ヒント、docstring の目的は、周りのコードではなく、このスキルの決まりに従う。

## 書くときに、まず意識すること

### 名前（可読性のため）

- 変数名は、2語以上で作る。できれば3〜4語以上を目指す。
- ただし、無駄に冗長にしない（型や、同じ語を繰り返さない）。
- 処理の手順よりも、文脈の上で大事な意味を表す語を選ぶ。特に、その値がどこから来たか（HTTP で別のサーバーから取得した、など）を大事にする（例: キューから取り出した文でも、もとは別のサーバーから取得した文なら `dequeued_prompts` ではなく `fetched_prompts`）。
- 情報を足しすぎて、名詞の名前や動詞の名前を文にしない。文になると、かえって読みにくい（例: `vlm_selected_function` → `selected_function_by_vlm`）。
- 真偽値以外の変数名は、名詞句にする。動詞を含むときは、目的語を中心の名詞にし、動作主を `by_〜` で表す（例: `selected_function_by_vlm`）。
- 名詞だけの変数名は、主語になる物か、目的語になる物かに応じて、能動か受動かの情報を入れる（例: `seat_monitor_thread`、`taken_prompts`）。
- 真偽値の名前は、文の形でもよい（例: `worker_is_seated`）。
- 関数名は、動詞と目的語で作る（例: `_care_for_worker_once`）。
- 名前を変えるときは、元の名前の単語が意味をよく表していれば、その単語を残し、「何の〜か」を表す語を足す（例: `streak` → `disagreeing_judgment_streak`）。
- 語と語の間は、`_` でつなぐ（クラス名は CapWords）。
- ソフトウェアエンジニアに通じる用語や略語（`mic`、`vlm`、`url`、`gpu`、`cnt`、`res` など）は、積極的に使ってよい。
- ただし、略語だけの1語の名前にしない（例: `cnt` → `retry_cnt`）。

### 先頭の `_`

- ファイルの中だけで使う関数と、クラスの中だけで使うメソッドの名前の先頭に、`_` を付ける。
- ファイルの中だけで使うモジュールの定数は、そのファイルの中に定義し、名前の先頭に `_` を付ける（例: `_CAMERA_INDEX`）。環境変数から読む定数でも、環境変数の名前は変えない。

### 型ヒント

- 引数、戻り値（何も返さないときは `-> None`）、モジュールの定数、ローカル変数、インスタンスの属性に、型ヒントを必ず付ける。
  - 例外: 文法の上で、その行の中に書けないところ（`for` の変数など）と、`self`、`cls`。

### docstring

- すべての関数、メソッド、クラスに書く。
- まず、その **目的**（なぜ、何のためにあるのか）を書く。処理の手順を言い換えるだけで終わらせない。

### 中身が1行だけの関数

- 中身が1行だけの関数は作らず、その1行を、呼び出し側に直接書く。
  - 例外: ログを出す関数のように、汎用性が高い関数。
  - 例外: 言語やフレームワークの都合で、関数として定義しなければならないもの。
  - 例外: プロジェクトのルールが決めた例外。

## 書いたあとの点検

次の項目を、Claude が自分で確かめる。

- [ ] 一語だけの変数名がない（ループの添字の `i`、`j` などの例外を除く）。
- [ ] 冗長な名前がない（型や、同じ語を繰り返していない）。
- [ ] 名前が、処理の手順ではなく、文脈の上で大事な意味（その値がどこから来たか、など）を表している。
- [ ] 情報を足しすぎて、文の形になった変数名や関数名がない（真偽値の名前を除く）。
- [ ] 動詞を含む変数名に、動作主と目的語の情報がある。
- [ ] 名詞だけの変数名に、必要なら、能動か受動かの情報がある。
- [ ] 真偽値の名前から、何が真なのかが読み取れる。
- [ ] 関数名が、動詞と目的語になっている。
- [ ] 変数名と関数名の語と語の間が、`_` でつながっている。
- [ ] 略語だけの1語の名前がない（略語そのものは、エンジニアに通じるものなら使ってよい）。
- [ ] ファイルの中だけで使う関数と、クラスの中だけで使うメソッドに、`_` が付いている。
- [ ] ファイルの中だけで使うモジュールの定数が、そのファイルの中に定義され、`_` が付いている。
- [ ] すべての引数、戻り値、モジュールの定数、ローカル変数、インスタンスの属性に、型ヒントがある（例外を除く）。
- [ ] すべての関数、メソッド、クラスに docstring があり、その目的が書いてある。
- [ ] 中身が1行だけの関数を、新しく作っていない（例外を除く）。
- [ ] 名前を変えたときは、リポジトリ全体を検索して、呼び出し、コメント、文書も直した。
- [ ] 構文の誤りがない（VS Code の診断で確かめる。使えないときは `python3 -m py_compile`）。

## レビューを頼まれたとき

- 「書いたあとの点検」の項目で、コードを見る。
- 名前の指摘を、細かな指摘として後回しにしない。
- 名前を長くすることだけが目的の指摘はしない。冗長な名前や、文になった名前は、指摘する。
- 指摘には、ファイル、行、直し方の案を添える。
- 指摘のあとで直すかどうかは、プロジェクトのルールにも従う。
