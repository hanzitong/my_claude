# 日本語の文書の修正

文書の中で、読み手が迷う文と箇条書きを見つけて直す。
言葉の修正では、決まり、事実、数値、日付、条件を変えない。

点検の観点と、直さずに保つものは、`references/checklist.md` にまとめてある。このファイルと checklist が食い違うときは、checklist に従う。

## 直すもの

必ず守る決まりは、次の5つである（2026-10-16 と 2026-10-19 に、ユーザーが指示した）。

- 箇条書きは、並列にする
- 項目の理由は、入れ子にして書く
- 補足の説明は、カッコに入れる
- 番号は、順序を表すときだけに使う
- 並列する項目は、粒度を揃える

特に重く見ることは、次の4つである（2026-10-16 と 2026-11-03 に、ユーザーが指示した）。

- 動詞ごとに、動作主（誰が）と動作対象（何を、何に）をはっきりさせる
- 動詞の修飾語（どこに、どこから、いつ、どのように）を、できるだけ充実させる
- 修飾語を、修飾先のできるだけ近くに置く
- 説明の前に、前提（何の話か、登場するもの、それぞれの役割、いまの状況）を書く

詳しくは、checklist の「直すもの」の節にある。

| 観点 | 直すもの | 優先度 |
|---|---|---|
| 並列と番号 | 並列になっていない箇条書き。入れ子になっていない理由。カッコに入っていない補足。粒度が揃っていない列挙。順序のない項目に付いた番号。番号のない手順 | 高 |
| 曖昧 | 2通り以上に読める文（動作主が2通り以上に取れる文、修飾語が修飾先から離れている文など）。前後の文と矛盾して読める文 | 高 |
| 不完全 | 動作主、動作対象、述語のどれかが書かれていない文。動詞の修飾語が足りず、読み手が補わないと動きが決まらない文。前提を書かずに本題に入っている説明。主語と述語がねじれている文 | 中 |
| 冗長 | 同じことを繰り返す文。消しても、読み手が何も失わない文 | 低 |
| 抽象 | 伝えたいことを言い切っていない文。読んでも、何をすればよいか分からない文 | 低 |

言葉を直しても解けない問題は、「内容」として分けて示す。内容の問題には、文書の間の食い違い、文書と実際のファイルの構成との食い違い、古い情報、事実の誤りがある。直すかは、ユーザーが決める。

## 手順

### 1. 範囲を決める

1. 対象のファイルやディレクトリを、ユーザーの指示から決める。ユーザーが指定していなければ、ユーザーに尋ねる。
2. 対象がワークスペースの外にあるときは、読む前にユーザーの承認を得る（社内のルール）。
3. 対象のファイルを一覧にする。Glob を使う。Glob を使えなければ、短い find のコマンドを1つだけ使う。
4. 一覧から、次のファイルを外す。外したファイルは開かない。
   - 認証情報のファイル（`.credentials.json`、`.env` など）
   - キャッシュ
   - バックアップ
   - ログ
   - 会話の記録
   - コード（.py、.sh など）
     - 例外: ユーザーに頼まれたときは、コードのファイルを開き、コメントだけを対象にする。

### 2. 点検を分担する

点検は、ja-reviewer エージェントに任せる。対象が少なくても任せる。
点検の結果だけを受け取れば、Claude は会話の文脈を節約できる。また、ja-reviewer は、書き手が文書を書いたときの文脈を知らないので、書き手の思い込みに気づきやすい。

1. 対象を、組に分ける。1つの組は、合わせて 1500 行程度にする。同じ話題のファイル（同じスキルの中のファイルなど）は、同じ組に入れる。
   - 理由: ja-reviewer が、ファイルの間の矛盾や、用語の揺れに気づけるようにするためである。
2. 組ごとに、ja-reviewer を起動する。複数の組は、1つのメッセージで同時に起動する。頼むときは、次のものを渡す。
   - 対象のファイルの絶対パス
   - 読み手（Claude への指示か、人が読む文書か）
   - ユーザーが特に気にしている点（あれば）

ja-reviewer を呼び出せないとき（Claude Code がまだ読み込んでいないときなど）は、general-purpose エージェントに頼む。指示には、次の2つを入れる。

- エージェントが、`~/.claude/agents/ja-reviewer.md` を読み、その内容に従うこと
- エージェントが、ファイルを変更しないこと

### 3. 修正案を示す

1. 返ってきた指摘を、1つの一覧にまとめる。同じ言い回しの指摘が複数のファイルにあれば、ユーザーに示す一覧では1行にまとめ、ファイルと行を並べる。
2. 指摘を、Claude も checklist で確かめる。意味が変わる案と、好みだけの言い換えは、一覧から外す。外したものは、理由を添えて、一覧の最後に示す。
3. 一覧の行を、優先度の高い観点から順に並べ、内容の指摘を最後に置く。各行には、ファイルと行、観点、いまの文、問題、修正案を書く。
4. ユーザーに一覧を示し、どこまで直すかを AskUserQuestion で尋ねる（すべて、内容以外、曖昧だけ、など）。
   - 例外: 指摘が多いときは、観点ごとの件数と代表例を示し、方針について承認を得てよい。

直すファイルが1つでも、ユーザーの承認を得てから直す。
ユーザーへの質問や説明の文も、checklist の基準で書く。特に、誰がするのか、誰が決めたのかを書く。

### 4. 直す

直すのは、ユーザーが承認した範囲だけである。

1. 対象が git で管理されていないときは、直す前に、対象のファイルを写しておく（~/.claude なら、`~/.claude/backup/<日付>-ja-revise/` に写す）。
   - 理由: 写しがないと、直す前の状態に戻せない。
2. 直す直前に、直すファイルを Read で読み直す。
   - 理由: 別のセッションが、ファイルを更新していることがある。
3. Edit で、1か所ずつ直す。sed やスクリプトで、まとめて置き換えない。

直すファイルが5つ以上あるときは、ファイルの組ごとに、サブエージェント（fork）に修正を分担させ、同時に進める。分担させるときは、次の決まりを守る。

- 各サブエージェントに、担当のファイルと、「いまの文 → 修正後の文」を、そのまま渡す。
- サブエージェントが言い回しを独自に変えないことを、指示に入れる。
- いまの文が見つからなければ、サブエージェントが直さずに報告することを、指示に入れる。
- 同じファイルを、2つのサブエージェントに渡さない。

### 5. 見直す

1. 直したファイルを、ja-reviewer にもう一度点検させる。直した箇所の、修正前と修正後の文を渡し、新しい曖昧さや、意味の変化がないかを確かめさせる。
2. 見直しで出た指摘のうち、直した箇所の誤り（承認した文との違いや、直したことで生まれた新しい曖昧さ）は、ユーザーに尋ねずに直し、報告に書く。それ以外の新しい指摘は、ユーザーに示し、承認を得てから直す。

### 6. 報告する

ユーザーに、次の表の形で報告する。

| 報告すること | 添えるもの |
|---|---|
| 直したファイル | ファイルごとの、直した箇所の数 |
| ユーザーが承認した案から変えたところ | 変えた理由 |
| 直さなかった指摘 | 直さなかった理由 |
| ユーザーがまだ決めていない「内容」の指摘 | ユーザーに決めてほしいこと |

## ユーザーの好みを残す

ユーザーが修正案を却下したときや、文体や言葉の好みを示したときは、このスキルを使う Claude が、ja-reviewer のメモリー（`~/.claude/agent-memory/ja-reviewer/MEMORY.md`）に書き足す。書き足すのは、ユーザーが却下した修正の型と却下の理由か、ユーザーが示した好みである。どの記録にも、日付をつける。
次の点検で、ja-reviewer が同じ型の修正を繰り返し提案しないようにするためである。
ja-reviewer は、メモリーを読むだけで、書き込まない。
多くのファイルに当てはまる好みは、checklist に足すかを、ユーザーに尋ねる。

## 付属のファイル

| ファイル | 内容 | 読むとき |
|---|---|---|
| `references/checklist.md` | 必ず守る決まり、特に重く見ること、直す観点、保つもの、直した例、修正案の書き方 | 点検の前。修正案をまとめるとき |
| `~/.claude/agents/ja-reviewer.md` | 点検をするエージェント | 点検や見直しを頼むとき |
