# 日本語の修正の観点

ja-revise スキルと ja-reviewer エージェントが、この checklist を使う。

- 点検の前に、「直すもの」と「保つもの」の節を読む。
- 修正案を書くときに、「修正案の書き方」の節を読む。
- 迷ったときに、「直した例」の節を見る。

---

## 直すもの

直す理由を、次の観点のどれかで説明できる文だけを直す。直す理由を説明できない言い換えは、好みの違いなので、修正案に挙げない。

### 必ず守る決まり

ユーザーが指示した決まりである（2026-10-16 に「厳守」「絶対」と指示し、2026-10-19 に書き方を決めた）。点検するときも、修正案を書くときも、例外を認めない。

- **箇条書きは、並列にする。** 1つの箇条書きには、並列の項目だけを並べる。手順の続きや、別の話題を、並列の項目に混ぜない。
- **項目の理由は、入れ子にして書く。** 項目に理由があるときは、その項目の下に、「理由:」で始まる入れ子の項目として書く。項目に例外があるときも、「例外:」で始まる入れ子の項目にする。
- **補足の説明は、カッコに入れる。** 項目の補足の説明（例、言い換え、出どころなど）は、カッコに入れる。カッコの中の補足は、一部の項目にだけ付いていてもよい。
- **番号は、順序を表すときだけに使う。** 番号（1、2、3）は、その順に行う手順と、順序に意味がある項目（優先度の順、まとめる順など）にだけ付ける。順序のない並列には、番号を付けず、「-」の箇条書きにする。
- **並列する項目は、粒度を揃える。** 並べる項目は、すべて単語か、すべて文にする。1つの項目に、2つ以上のことを入れない。理由、例外、補足のほかに、ある項目にだけ文を足さない。

これらの決まりは、箇条書きの項目にも、文の中の列挙（「A、B、C」）にも当てる。入れ子の書き方は、次の例のとおりである。

```markdown
- 同じ条件で複数回測り、平均だけでなく、中央値と最大を書く。
  - 理由: ロボットの振る舞いを決めるのは、最大の遅れである。
```

### 特に重く見ること

ユーザーが指示したことである（2026-10-16、2026-10-19、2026-11-03）。点検するときも、修正案を書くときも、まずこれを確かめる。同じ決まりは、`~/.claude/rules/japanese-document-style.md` にもある。

- **動詞ごとに、動作主と動作対象をはっきりさせる。** 動作主は「誰が」、動作対象は「何を」「何に」である。1文に動詞が2つ以上あるときは、動詞ごとに確かめる。
- **動詞の修飾語を、できるだけ充実させる。** 動作主と動作対象に加えて、どこに、どこから、いつ、どのように、を書く。主語だけでは足りない（「`_report_thread_death` が、ログを出す」→「`_report_thread_death` が、標準出力に1行のログを出す」）。
  - 理由: 2026-11-03 に、ユーザーが「『_report_thread_death がログを出します』ではまだ不十分です。『_report_thread_death が XXX にログを出します』まで言って下さい」と指示し、文書の点検の観点にも入れるよう指示した。
- **修飾語を、修飾先のできるだけ近くに置く。** 修飾語と修飾先の間に、別の語句を挟まない。理由や例外の文は、それが説明する文の直後に置く。
- **説明の前に、前提を書く。** 読み手を、その話について何も知らない、外から来た人だと思って書く。文書や節の冒頭に、前提（何の話か、登場するもの、それぞれの役割、いまの状況）を置き、そのあとで本題を書く。
  - 理由: 2026-11-03 に、ユーザーが「説明の前には必ず前提の説明を行って下さい。私が何もわからない外から来たひとだと思って説明してください」と指示し、文書の点検の観点にも入れるよう指示した。
  - 例外: 文書の冒頭に「この文書について」のような前提の節がすでにあるときは、その節を前提として使う。

Claude は、Claude への指示の文の中で、動作主を書いていない動詞を、自分がすることとして読む。そのため、動作主は、次のように扱う。

- Claude 以外（ユーザー、サブエージェント、別のセッションなど）がする動作には、受け身の文でも、動作主を必ず書く（「頼まれたとき」→「ユーザーに頼まれたとき」）。
- 受け身の文で動作主を書きにくいときは、能動の文にする（「ログが消された」→「起動のスクリプトが、ログを消した」）。
- 動作主が分からないときは、推測で補わない。ユーザーに確かめるか、分からないことを文に書く（「推定」「未確認」など）。

### 並列と番号（優先度: 高）

「必ず守る決まり」に反するものである。見つけたら、必ず修正案に挙げる。

| 型 | 見つけ方 |
|---|---|
| 並列でない箇条書き | 1つの箇条書きに、並列でないもの（手順の続き、別の話題）が混ざっている |
| 入れ子になっていない理由 | 1つの項目の理由や例外が、入れ子の項目でなく、項目の中の文や、箇条書きの外の文として書かれている |
| カッコに入っていない補足 | 項目の補足の説明（例、言い換え、出どころなど）が、カッコでなく、別の文として書かれている |
| 単語と文の混在 | 箇条書きや、文の中の列挙で、単語の項目と文の項目が混ざっている（「決め手、誰が決めたか、前提」） |
| 粒度の違い | 1つの項目にだけ、2つ以上のことが入っている（「- 認証情報のファイル」と「- キャッシュ、バックアップ、ログ」） |
| 順序のない番号 | 順序のない並列に、番号が付いている |
| 番号のない手順 | その順に行う手順が、番号のない箇条書きで書かれている |

### 曖昧（優先度: 高）

読み手が、書き手と違う意味に取りうる文である。Claude への指示では、誤った動きにつながる。

| 型 | 見つけ方 |
|---|---|
| 動作主が2通りに取れる | 1つの動詞について、する人が2通り以上に取れる（「メモリーに書き足す」のが、スキルを使う Claude か、エージェントか） |
| 修飾語が修飾先から離れている | 修飾語と修飾先の間に、別の語句が挟まっている（「速く、カメラから届いた画像を処理する」→「カメラから届いた画像を、速く処理する」）。文の単位でも同じで、理由や例外の文は、それが説明する文の直後に置く |
| 係り先が2通りに取れる | 「A の B の C」「A と、B の C」のように、修飾がどこに係るかが決まらない |
| 指す先が分からない | 「この」「その」「〜する側」が何を指すかが、直前の文だけでは決まらない |
| 決まりと例外が食い違う | ある文が「〜しない」と言い切り、別の文が例外を認めている。例外の条件を、言い切りの文に入れる |
| 同じ語を2つの意味で使う | 近くで別の意味に使った語（「メモ」「確認」など）が、どちらを指すかが分からない |
| 説明のない言葉 | その文書の中だけで通じる言葉（「正のファイル」「素通し」など）が、説明なしに出てくる |
| 漠然とした言葉 | 「忙しさ」「適切に」「うまく」など、何を測るのか、何をするのかが決まらない |
| 否定の範囲が分からない | 「〜でも、〜しない」で、何をしないのかが決まらない |

### 不完全（優先度: 中）

読み手が、抜けた語を補わないと読めない文である。

| 型 | 見つけ方 |
|---|---|
| 動作主がない | 誰がするのか、誰の判断なのかが、その文と直前の文から決まらない（「〜と考えている」） |
| 動作対象がない | 何を、何に対してするのかが分からない（「除くか、分けて書く」では、何を除くのかが分からない） |
| 修飾語が足りない | 動詞に、どこに、どこから、いつ、どのように、が書かれておらず、読み手が補わないと動きが決まらない（「ログを出す」では、どこに出すのかが分からない） |
| 前提がない | 説明や手順の前に、何の話か、登場するもの、それぞれの役割、いまの状況が書かれていない。外から来た読み手が、本題を読み始められない |
| 述語がない | 箇条書きや表の中の文が名詞で終わり、何をするのかが分からない |
| ねじれ | 主語と述語が対応していない（「仕様書は、外から見た振る舞いである」） |
| 「〜たり」が1回だけ | 「抽象的だったり曖昧な場合」 |

### 冗長（優先度: 低）

| 型 | 見つけ方 |
|---|---|
| 繰り返し | 見出し、すぐ前の文、すぐあとの箇条書きと、同じことを言っている |
| 重なった言い方 | 「確認を確かめる」「目安には、目安を書く」 |
| 何も足さない前置き | 消しても、読み手が失うものがない文 |
| 回りくどい言い方 | 二重の否定。「〜ということである」「〜するものとする」 |
| 文を並べた列挙 | 「。」で区切った文を、1行に並べた列挙。箇条書きにする |

### 抽象（優先度: 低）

伝えたいことの本質を、1文で言い切る。

| 型 | 直し方 |
|---|---|
| 言い切っていない | 「〜を示すものであり、〜を求めるものではない」を、「〜は求めない」と言い切る |
| 理由がぼやけている | 「〜を避けるためである」の「〜」が抽象的な言葉なら、何が起きるのを防ぐのかを書く |
| 抽象的な言葉だけで示している | 「逃げ道になる言葉」のような表現には、例を添える（「場合によっては」「必要に応じて」など） |
| 何が同じかが分からない | 「同じ立場にある」を、何が同じなのか（「同じ偏りを持つ」）で書く |

### 内容（直すかは、ユーザーが決める）

言葉を直しても解けない問題である。見つけたら報告するが、言葉の修正とは分けて示す。

- 文書の間の食い違い
- 文書と、実際のファイルの構成との食い違い
- 古い情報（いまはない仕組みの説明など）
- 事実の誤り（ライブラリの動き、コマンドの使い方など）

事実の誤りかどうかが確かでないものは、「確認が必要」とする。

## 保つもの（直さないもの）

- **意味**: 修正の前と後で、読み手のすることを変えない（決まり、事実、数値、日付、条件を変えない）。
- **文体**: ファイルごとの文体（である調、です・ます調）を保ち、ユーザーに頼まれない限り、ファイルの間で揃えない。
- **言葉の選び方**: 書き手が選んだ和語（「確かめる」「移り変わり」「働きかける側」）を、漢語や片仮名の用語（「確認する」「遷移」「イニシエーター」）に置き換えない。
- **読点**: 読点の多い書き方（「ADR を書くとき、直すときは、」）を、読点を減らすだけの目的で直さない。
- **1文に1つのこと**: 長い文は分けてよいが、短い文をつなげて長い文にはしない。
- **書式**: frontmatter のキー（name、paths、tools など）、コードブロックの中身、パス、コマンド、URL を変えない。
- **表**: 表の列の数を変えない。
- **description**: スキルやエージェントの description は、言葉を直してよい。
  - 例外: 使う場面を示す言葉（「〜と言われたとき」「〜のあとに使う」）は、落とさない。
- **見本**: 見本（`example.md` など）の中で、見本として書かれた文は直さない（ひな形の中の説明の文は、直してよい）。
- **ユーザーが自分で書いた文**: 議事録や仕様書などで、ユーザーが自分で書いた文は、ユーザーに頼まれた範囲だけを直す。

## 直した例

|---|---|---|---|
| 並列と番号（粒度の違い） | - 認証情報のファイル（〜） ／ - キャッシュ、バックアップ、ログ、会話の記録 ／ - コード（.py、.sh など）。コードのコメントは、頼まれたときだけ対象にする | 1行に1種類ずつ並べた。例外の文は、「例外:」で始まる入れ子の項目にした | 項目ごとに、含む種類の数が違っていた。1つの項目にだけ、例外の文が付いていた |
| 並列と番号（単語と文の混在） | 通信が切れた、時間切れ、プロセスが止まった、ときに | 通信が切れたとき、時間切れになったとき、プロセスが止まったときに | 名詞と文が混ざり、「ときに」の係り方が分からない |
| 曖昧（動作主が2通り） | （スキルとエージェントの両方に）ユーザーの好みを、メモリーに書き足す | このスキルを使う Claude が、ja-reviewer のメモリーに書き足す。ja-reviewer は、メモリーを読むだけで、書き込まない。 | 書き足すのが誰かが、2つのファイルで違って読めた |

| 不完全（動作対象） | 除くか、分けて書く | その値は、集計から除くか、ほかと分けて書く | 何を除くのかが分からない |
| 不完全（動作主） | 〜は求められていないと考えている。 | 〜は求められていない（推定。文書での明記は未確認）。 | 誰の考えかが分からない。動作主を推測で補わず、確かさを書いた |
| 冗長（重なった言い方） | 「採用にする前の確認」を確かめる | 「採用にする前の確認」の5項目を満たすかを確かめる | 「確認を確かめる」が重なっている |
| 冗長（前置き） | この会社の環境に特有の、特殊な使い方である。 | （消した） | 直後の箇条書きが、同じことを具体的に書いている |
| 抽象（言い切っていない） | 観点を示すものであり、製品化のための作り込みを求めるものではない。 | 確かめる観点を示すためのものであり、製品化のための作り込み（エラー処理の細部、テストの充実など）は求めない。 | 何を求めないのかを、例を添えて言い切った |
| 抽象（理由がぼやけている） | 素通しを避けるためである。 | 点検を飛ばした観点がないことを示すためである。 | 「素通し」では、何を防ぐのかが分からない |
| 内容 | （README）コードの変更を避ける決まりは、フックの代わりに `~/ROBO_NEXT/.claude/rules/robo-system-code.md` が受け持ちます。 | フックの代わりに、次のスキルが同じスクリプトを実行します。（スキルの表を足した） | 実際の構成と食い違っていた。言葉の修正とは分けて、ユーザーの承認を得て直した |

## 修正案の書き方

- 修正案は、そのまま置き換えられる文で書く（「〜を明確にする」のような、方針だけの案にしない）。
- 修正案でも、「必ず守る決まり」と「特に重く見ること」を守る。
- 「いまの文」には、置き換える範囲を、ファイルの中で一意に決まる長さで、そのまま引用する。
  - 理由: ja-revise を使う Claude が、その文を Edit でそのまま置き換えるためである。
- 1つの指摘に、修正案は1つにする。
  - 例外: 迷うときは、2つ目を「別案」として添えてよい。
- 動作主や意図が分からないときは、推測で補わず、「確認が必要」として、ユーザーに尋ねる問いを書く。
- 修正案そのものも、この checklist で確かめ、新しい曖昧さや冗長さを持ち込まない。
